# BlindBid — Sealed-Bid Auction Agent

A sealed-bid first-price auction agent for **Agent Games** (zkVerify) — Wildcard track.

It runs a whole auction autonomously — create, bid, reveal, settle — and **never sees a bid before the reveal**. A bidder commits to a hidden bid with a Groth16 proof that it is in range; the agent verifies the proof, and only after the close does anyone learn the bids.

## What it does

A sealed-bid auction lives or dies on one rule: bids stay hidden until the close. If the auctioneer can see them early, the auction is gameable. But the auctioneer must still know each hidden bid is *valid* — in range, really committed, registered before the close. BlindBid proves all of that without revealing the bid:

1. **Create** — `POST /api/auction` with `{item, minBid, maxBid, closeAt}`. The agent signs the auction config into a ticket, so the config cannot be tampered with later.
2. **Bid** — `POST /api/bid` with `{ticket, bidder, commitment, proof, publicSignals}`. The agent checks the ticket, checks the auction is still open, verifies the Groth16 proof against the **registered** verification key, and checks what was proven: `inRange == 1`, the proven commitment equals the claimed one, and the proven bounds equal the auction's bounds. A proof made with a substituted key, a tampered commitment, or an out-of-range bid is rejected. An accepted bid returns a **signed bid receipt** — proof the bid was registered before the close.
3. **Reveal** — `POST /api/reveal` with `{ticket, bidReceipt, bid, salt}`, only after the close time. The agent verifies the receipt, checks it was issued before the close, and recomputes `Poseidon(bid, salt)` — it must match the committed commitment exactly. A wrong salt or a forged receipt is rejected.
4. **Settle** — `POST /api/settle` with `{ticket, reveals}`. The agent re-verifies every reveal from scratch, rejects duplicate bidders (one bid per bidder, enforced here where all reveals are visible), and signs the settlement: the highest revealed bid wins (ties go to the earliest registered bid).

A proof can verify perfectly and still authorize the wrong action, so verification is necessary but never sufficient on its own — the agent checks what was proven, what was committed, and when it was registered.

## The problem it solves

Sealed-bid auctions are the cleanest case where privacy is load-bearing: the whole point is that nobody — not the auctioneer, not the other bidders — sees a bid before the close. At the same time, the auctioneer cannot accept blind numbers: a bid outside the allowed range, a bid changed after the reveal, or a bid registered after the close all break the auction. BlindBid is a complete, runnable implementation of an agent that enforces all of it with zero-knowledge proofs and signed receipts: real circuit, real proofs, a real HTTPS endpoint, and a demo that shows every attack being rejected.

## The circuit

`circuits/blindbid.circom` (Circom 2.2.3, Groth16/BN128, 592 constraints):

> “I know a bid between `minBid` and `maxBid`, hidden inside `commitment = Poseidon(bid, salt)` — without revealing the bid.”

- `bid` — private input (never leaves the bidder until the reveal).
- `salt` — private input (a random 32-bit salt, so equal bids still commit differently).
- `minBid`, `maxBid` — public inputs.
- `inRange` — public output, 1 when `minBid <= bid <= maxBid`, 0 otherwise. A proof with `inRange = 0` still verifies (it is a true statement about an out-of-range bid) — the agent rejects it because `inRange` must be 1.
- `commitment` — public output, `Poseidon(bid, salt)`.
- Public signals, snarkjs output-then-public order: `[inRange, commitment, minBid, maxBid]`.
- Values are 32-bit, which covers any VFY amount in play.

The verification key is committed in `lib/verification_key.json` (fingerprint shown by `GET /api/circuit-info`). The proving key and wasm are regenerated by `npm run setup`.

## Stateless by design

The agent keeps **no database**. Every state transition is carried by a signed receipt (HMAC-SHA256 over a canonical JSON encoding):

| Receipt | Proves |
|---|---|
| Auction ticket | the auction config was signed by the agent and not tampered with |
| Bid receipt | this bid was registered before the close time |
| Reveal receipt | this revealed bid is the one that was committed |
| Settlement | the winner was recomputed from verified reveals |

That is what makes the agent deployable on serverless (Vercel) with no shared state. Receipts are keyed by `AGENT_SECRET` when set; in demo mode (no secret) they use a public demo key — fine for the demo, never for a registered agent. Incoming `POST` requests are HMAC-authenticated the same way as the Gatekeeper project (signature `HMAC-SHA256(secret, timestamp + "." + rawBody)`, timestamps older than 5 minutes rejected, responses signed).

## Live demo

Run it locally (`npm start`, then open http://localhost:3000) or deploy it to Vercel (see below). The demo page:

- **Runs a full auction** — creates an auction closing in 45 seconds, submits 3 sealed bids (commitments only, amounts hidden), counts down to the close, reveals all three, and settles the winner (bob, 920).
- **Fires 12 canned payloads** — one per attack — and shows each verdict:

| Example | What is tampered | Expected verdict |
|---|---|---|
| Valid bid | nothing — real proof, bid 750 in [100, 1000] | **ACCEPT** |
| Out-of-range bid | proof says inRange=0 (bid 1500 > max 1000) | REJECT |
| Tampered commitment | claimed commitment ≠ proven commitment | REJECT |
| VK substitution | proof made with a different proving key | REJECT |
| Fake proof | random proof values | REJECT |
| Bid after close | valid proof, auction already closed | REJECT |
| Valid reveal | nothing — correct bid + salt | **ACCEPT** |
| Wrong salt | reveal does not match the commitment | REJECT |
| Reveal before close | valid receipt, auction still open | REJECT |
| Valid settlement | 3 valid reveals | **ACCEPT (bob 920)** |
| Duplicate bidder | same bidder twice in the reveals | REJECT |
| Tampered reveal | bob reveals 950 instead of his committed 920 | REJECT |

You can also paste your own payload into the demo page and send it to any endpoint. The demo bids are public by design so anyone can run the demo — a real bidder generates their own proof with `node scripts/prove.js <bid> <salt> <minBid> <maxBid>` and keeps `bid` + `salt` secret until the reveal.

## Run it locally

```bash
npm install
npm run setup   # compile circuit, trusted setup, verification key, canned proofs
npm test        # end-to-end tests over HTTP (22 tests)
npm start       # http://localhost:3000
```

Environment variables:

| Variable | Meaning |
|---|---|
| `PORT` | Port to listen on (default 3000). |
| `AGENT_SECRET` | HMAC secret. When set, the endpoint enforces HMAC on incoming requests, signs its responses, and keys every ticket/receipt with it. When unset, the server runs in **demo mode** (HMAC not enforced, tickets use a public demo key) — fine for the demo, never for a registered agent. |

## The endpoints

`POST /api/auction` — create an auction. Request:

```json
{ "auctionId": "demo-live-1", "item": "Rare VFY Art #1", "minBid": 100, "maxBid": 1000, "closeAt": 1795000000000 }
```

Response: `{ "decision": "ACCEPT", "ticket": { "auction": {...}, "signature": "…" } }`.

`POST /api/bid` — submit a sealed bid. Request:

```json
{
  "ticket": { "auction": {...}, "signature": "…" },
  "bidder": "alice",
  "commitment": "8484248555334419206114235833484269937060675722096139228833488434578173407393",
  "proof": { "pi_a": ["…"], "pi_b": [["…"]], "pi_c": ["…"], "protocol": "groth16", "curve": "bn128" },
  "publicSignals": ["1", "8484248555334419206114235833484269937060675722096139228833488434578173407393", "100", "1000"]
}
```

Response: `{ "decision": "ACCEPT", "receipt": { "auctionId", "bidder", "commitment", "bidAt", "signature" }, "checks": {...} }`.

`POST /api/reveal` — reveal a bid after the close. Request:

```json
{ "ticket": {...}, "bidReceipt": {...}, "bid": 750, "salt": 12345 }
```

`POST /api/settle` — settle a closed auction. Request:

```json
{ "ticket": {...}, "reveals": [{ "bidReceipt": {...}, "revealReceipt": {...}, "bid": 920, "salt": 777 }] }
```

`GET /api/auction?ticket=<url-encoded JSON>` — auction status (`open`/`closed`). `GET /health` and `GET /healthz` — liveness. `GET /api/circuit-info` — circuit + verification-key fingerprint.

Headers (when `AGENT_SECRET` is set):

```
x-agentgames-signature: HMAC-SHA256(secret, timestamp + "." + rawBody)  (hex)
x-agentgames-timestamp: unix seconds (max 5 minutes old)
```

## Trust notes (honest boundaries)

- **Trusted setup is local.** The Powers of Tau file (`circuits/pot12_final.ptau`) was generated locally (snarkjs powersoftau, power 12, one contribution) because the public Hermez ceremony file returns AccessDenied from this environment. The ceremony is real Groth16 setup, just a local one. To use the multi-party Hermez ceremony instead, drop a `powersOfTau28_hez_final_*.ptau` file in as `circuits/pot12_final.ptau` and re-run `npm run setup`.
- **Demo mode is demo mode.** Without `AGENT_SECRET`, HMAC is not enforced and tickets/receipts use a public demo key. The demo is fully runnable that way; a registered agent always sets `AGENT_SECRET`.
- **One bid per bidder is enforced at settlement**, where all reveals are visible. A stateless agent cannot enforce it at bid time (it keeps no bidder list); a production deployment with a database would enforce it at bid time too. The crypto still binds every reveal to its commitment either way.
- **Second Wildcard entry.** This is a second, separate Wildcard entry from the same account (the first is the Universal Proof Gatekeeper, already submitted and pending). The dashboard presents a fresh "New submission" form for Wildcard and the site states no per-account entry limit in visible text, but backend acceptance of a second entry is unproven — this build is submission-ready either way.
